[README.md](https://github.com/user-attachments/files/33029111/README.md)# NWIS — Nearby Wells Intelligence System

**Proactive drilling-risk intelligence from offset-well history.**

NWIS ingests drilling telemetry, well logs, and daily drilling reports; extracts structured
formation and event data from documents; correlates the active well against nearby wells;
and serves explainable risk predictions with per-well cross-validation.

Built for **SIH 2026 · Problem Statement 121 · Oil India Limited**.

## The problem

Drilling decisions are made against incomplete information. A driller reaches a formation
that has been drilled before — often several kilometres away, by a different rig, under
different mud conditions — and the knowledge that would inform the decision exists only in
paper logs, scanned reports, and personal experience.

Three things make that knowledge hard to use:

1. **It is scattered.** Daily drilling reports, mud programmes, cementing job summaries,
   and event logs are separate documents in separate formats, much of them scanned images.
2. **It is not comparable.** Offset wells are described in different depth references. An
   interval at 2,850 m MD in one well is not 2,850 m in another; without explicit
   correlation, comparing them produces confident nonsense.
3. **It is retrospective.** Reports describe what happened. Nothing surfaces what is likely
   to happen over the next few hundred metres *while* the bit is still running.

NWIS addresses all three.

## What NWIS does

| Capability | Description |
|---|---|
| **Ingest** | Well headers, formation tops, telemetry time series, events, documents |
| **Extract** | Structured formation, depth, and event data from unstructured reports |
| **Correlate** | Rank offset wells by geological and pressure similarity; correlate depth |
| **Search** | Hybrid lexical and semantic retrieval across every ingested artefact |
| **Predict** | Per-risk classifiers and a non-productive-time regressor, validated on held-out wells |
| **Explain** | Every score decomposes into the features that produced it |
| **Alert** | Threshold-based alerting with suppression and measured effectiveness |

A **single Node.js process** serves the API and the built frontend. There is no message
broker, no search service, and no Python runtime.

```
│  Express 5 API                                                   │

├──────────────────────────────────────────────────────────────────┤
│  Domain                                                          │
│  correlation/  offsets · sections · compare · lookAhead          │
│  alerts/       engine · rules · effectiveness                    │
│  ml/           train · serve · explain · registry · artifacts     │
│  nlp/          preprocess · segment · extract · relations         │
│  search/       embed · store · retrieve                          │
├──────────────────────────────────────────────────────────────────┤
│  Data                                                            │
│  repositories/  typed access over the relational schema          │
│  db/            SQLite (better-sqlite3) · migrations · geo UDFs   │
└────────────────────────────┬─────────────────────────────────────┘
                             │

```

**Runtime store is SQLite; PostgreSQL + PostGIS + pgvector is the production target.**
SQLite keeps the demo single-process and zero-install. Every query goes through a
repository layer, so the Postgres migration is a driver swap rather than a rewrite. The
schema is written to be portable: PostGIS geography types replace the SQLite lat/lon
columns, and `pgvector` replaces the sparse TF-IDF vectors.

### Middleware stack

`helmet` · `cors` (explicit allowlist) · `express-rate-limit` · `compression` · `pino-http`
request logging · `zod` request validation · `multer` file upload.

### The depth-reference rule

**This is the single most important invariant in the schema.**

Every depth column carries an explicit `depth_reference`:

```
depth_md_m   + depth_reference = 'MD'      measured depth
depth_tvd_m  + depth_reference = 'TVD'     true vertical depth
depth_tvdss_m + depth_reference = 'TVDSS'  true vertical depth subsea
```

MD, TVD, and TVDSS are **never compared across wells** without an explicit correlation
first. A repository method that returns two wells' depths side by side is required to name
the reference it is comparing in, and the UI states it on screen. An interval at 2,850 m MD
in well A-17 and 2,850 m MD in well B-04 are different points in space; the correlation
table is what relates them.

## Machine learning

**[built]** Seven models across three families, trained in **pure Node.js** — no Python, no
scikit-learn, no model server.

### Why no Python

The constraint is a single `npm run api` process on operator hardware, with no container
runtime and no GPU. Training in Node keeps one toolchain, one dependency tree, and one
deployment story, and it makes every model inspectable: the artifacts are plain JSON that
can be read line by line, diffed in git, and audited by a domain expert who does not write
Python.

The artifact format is deliberately generic — a `kind`, a `featureVersion`, a feature list,
a metrics block, and a model card — so **a scikit-learn pipeline trained outside this
codebase drops in unchanged**, provided it emits the same envelope.

### Algorithm layer

Written from scratch in `server/ml/algorithms/`:

| Module | Contents |
|---|---|
| `linalg.js` | Numeric primitives, safe numerics |
| `metrics.js` | ROC AUC, average precision, RMSE, R², **bootstrap confidence intervals** |
| `logistic.js` | L2 logistic regression, Adam, Platt calibration |
| `tree.js` | CART with single-sorted-sweep split search, stochastic boosting support |
| `gbdt.js` | Gradient boosting, leaf shrinkage, row subsampling |
| `isolationForest.js` | Per-well isolation forest with context smoothing |
| `cv.js` | Grouped k-fold and holdout splitting **by well** |

### Validation methodology

Cross-validation folds are grouped **by well**, never by row. A row-level split leaks:
depth intervals from the same well are correlated, so a model scores well on rows it has
effectively already seen. Grouping by well means every evaluation is on **genuinely unseen
wells**.

Candidate algorithms compete on held-out AUC and the winner is promoted. The runner-up's
score is recorded in the model card — losing is reported, not hidden.

### Held-out results

| ↳ runner-up | GBDT | | | 0.6599 | | | |
| Kick | logistic | 8,239 | 9.6 | **0.9603** | 0.952–0.966 | 0.814 | thr 0.907 → 79% / 75% |
| ↳ runner-up | GBDT | | | 0.8300 | | | |
| Stuck Pipe | logistic | 12,564 | 40.1 | **0.9349** | 0.931–0.939 | 0.925 | thr 0.696 → 87% / 80% |
| ↳ runner-up | GBDT | | | 0.6795 | | | |
| Torque Spike | logistic | 10,457 | 24.9 | **0.9063** | 0.900–0.913 | 0.769 | thr 0.512 → 61% / 80% |
| ↳ runner-up | GBDT | | | 0.7161 | | | |
| NPT estimate | GBDT | — | — | RMSE **12.18 h** vs 12.61 h baseline | | | R² 0.068 |
| Formation Risk | Isolation Forest | — | — | separation AUC 0.597 | | | thr = top 5% quantile |
| Cementing Issue | logistic | 288 | — | 0.5857 | 0.495–0.658 | — | **not activated** |

**Three findings reported rather than buried:**

1. **Logistic regression beat gradient boosting on all four classifiers** — often by a wide
   margin. The features are engineered ratios with near-monotone relationships to risk;
   boosting spends its capacity fitting noise in a problem that a linear boundary in logit
   space already solves. The booster ships as the recorded runner-up, not as the default.
2. **Cementing Issue fails its own deployment gate** and is registered **but not activated**.
   With 288 rows across 48 wells its operating point reaches 0% precision and does not beat
   flagging every interval. Activating it would push known-useless scores into the alert
   engine, where the cost is an operator's attention.
3. **The NPT regressor beats its baseline only slightly** (R² 0.068). Real, but modest, and
   the model card says so.

### Deployment gate

A model whose operating point cannot beat "flag every depth interval" is **not activated**,
however good its AUC looks. The gate is evaluated during evaluation and enforced by the
trainer:

```js
metrics.deploymentGate = {
  usable,                // beats flag-everything AND ranking not inverted
  beatsAlwaysAlert,
  rankingNotInverted,    // AUC >= 0.5
  reasons: [...],        // human-readable, shown in the training summary
};
```

### Explainability

Every score decomposes. For logistic models the contribution of each feature is exact
(`contribution = weight × value`), not an approximation; for boosted models the path
through the trees is reported leaf by leaf. Explanations are paired with drilling-unit
guidance — what the number means in operational terms, not just which features moved it.

### Model artifacts

Training writes versioned bundles to `ml/artifacts/`, committed to git:

```
ml/artifacts/
  manifest.json                     active version per model
  nwis_mud_loss_risk@1.0.1.json
  nwis_kick_risk@1.0.1.json
  nwis_stuck_pipe_risk@1.0.1.json
  nwis_torque_spike_risk@1.0.1.json
  nwis_npt_estimate@1.0.1.json
  nwis_formation_risk_anomaly@1.0.1.json
```

Each bundle carries its metrics, model card, limitations, and artifact in **one file**, so a
version is always read as a unit — a card describing a different artifact than the one
beside it is worse than no card at all.

```bash
npm run ml:train      # ~330 s, 4 folds, 60 boosting rounds
```

## Document intelligence

**[planned]** — *the problem-statement headline capability. No implementation exists yet.*

This is the largest remaining gap. The target pipeline:

1. **Acquire** — daily drilling reports, mud programmes, cementing job summaries, bit logs
2. **Text layer** — native PDF text extraction via `pdfjs-dist`; OCR via lazy-loaded
   `tesseract.js` for scanned pages only, with a per-page flag recording which path produced
   the text
3. **Segment** — split into typed sections (drilling summary, formation tops, mud, incidents)
4. **Extract** — deterministic rule-and-regex extraction of formations, depths, events,
   durations, and mud properties against a drilling ontology
5. **Relations** — link extracted entities to wells, intervals, and telemetry
6. **Score confidence** — per-extraction, from pattern specificity and corroboration
7. **LLM assist** — optional and pluggable, **never load-bearing**: the deterministic
   extractive path stays authoritative and works with no model available

**Quality gate:** `npm run nlp:evaluate` scores the real pipeline against generator ground
truth and reports precision/recall per entity type. Extraction quality is measured, not
asserted.

**Residency:** an LLM may only be used if it runs on-premises. The policy is unresolved
(see [R4](#open-risks)).

## Search and retrieval

**[built]** Hybrid retrieval combining sparse lexical and dense signals, fused with
**Reciprocal Rank Fusion**.

| Stage | Implementation |
|---|---|
| Lexical | SQLite **FTS5** with BM25, `porter unicode61 remove_diacritics 2` |
| Vector | Sparse TF-IDF, L2-normalised, weighted term vectors |
| Fusion | Reciprocal Rank Fusion over both ranked lists |
| Corpus | `knowledge_items` — events, lessons, document chunks, well sections, mud programmes |

Why sparse TF-IDF rather than a transformer embedding service: it runs on-premises, needs
no model server, adds no latency, and is fully auditable. It is also honest about its
limits — it matches terminology, not meaning, and says so. `pgvector` is the upgrade path
when embedding infrastructure exists.

The index is maintained by explicit `indexKnowledgeItem` calls on every write path, not by
database triggers, so indexing behaviour is visible in application code and testable.

### Theming — light and dark

**[built]** Colour is defined as **41 semantic tokens** in `src/style.css`, not as hex values
scattered through rules. Switching themes flips one attribute on `<html>`:

```css
:root                  { --bg:#131214; --fg:#e6e9e4; /* … 41 tokens */ }
[data-theme='light']   { --bg:#f2f3ef; --fg:#262a22; /* … 41 tokens */ }
```

Consequences worth having:

- **A hex literal in a rule is a bug.** It cannot respond to the theme. The one-shot codemod
  (`scripts/add-light-theme.mjs`) rewrote all 246 hardcoded colours and **fails loudly** if
  any colour is unaccounted for, so a new colour has to enter as a token.
- The OS preference is followed until the user chooses explicitly; the choice persists in
  `localStorage`.
- A pre-paint script in `index.html` sets the theme **before React mounts**, so a light-theme
  user never sees a dark flash on reload.
- Native widgets — scrollbars, date pickers, autofill — follow `color-scheme`.
- The toggle is a real button with an accessible name and pressed state, not an icon-only
  glyph.

### Charts and map

Recharts for depth correlation and telemetry; Leaflet with OpenStreetMap tiles for the field
map. Inline chart and map colours are tokenised too, so charts follow the theme.

> Map tiles come from OpenStreetMap's public service and need internet access. In an
> on-premises deployment these are replaced by an internal tile source.

## Testing

**[planned]** No automated test suite exists yet. `vitest` and `supertest` are not installed.

Planned coverage, in priority order:

1. **Unit** — the ML algorithm layer (logistic, tree, GBDT, isolation forest, metrics, CV),
   which is the component where a silent numerical bug produces plausible-looking nonsense
2. **Integration** — migrations apply cleanly; repositories round-trip; ingest is idempotent
3. **Contract** — every route's validation and error shape
4. **Quality gates** — `nlp:evaluate` against ground truth; model deployment gates

> Three bugs found during development were exactly the kind a unit test catches and a
> screenshot does not: an inverted gradient sign in GBDT (AUC 0.10), an isolation forest
> choosing the *most balanced* split and therefore having no discriminative power at all,
> and a threshold set above the model's own maximum score. All three produced plausible
> output and silently wrong numbers. This is why the algorithm layer is the first test
> target.

## Design decisions

**SQLite now, Postgres later.** Every query goes through a repository, so the target store
is a driver swap. Geo columns and vector columns are the only genuinely dialect-specific
parts, and both have documented PostGIS/pgvector equivalents.

**Node-only ML.** One toolchain, no container, no GPU, artifacts a domain expert can read.

**Sparse TF-IDF + BM25, fused.** On-premises, auditable, no model server. Stated limits.

**Depth reference is never implicit.** Enforced in the schema, named in every repository
method, displayed in the UI.

**Corpus labels are causally derived.** Mud loss is emitted because a generated ECD crossed
a generated fracture gradient — not because a label said "mud loss". That is what makes the
extraction and detection pipeline testable end to end.

**The search index is application code.** Explicit calls on every write path, not triggers.

**The LLM is optional.** The deterministic extractive path stays authoritative and fully
functional with no model available.

**Failing models ship as failures.** A model that loses to its baseline is registered with
its reasons and left inactive.

## Limitations

Stated plainly, because a system that hides these is harder to trust than one that names
them.

**The headline number is not a field result.** ROC AUC 0.9886 for mud loss measures whether
the pipeline is internally consistent. Event labels are generated from the same channels the
extractor reads, so a high score partly reflects that the simulator is self-consistent. It is
**not** evidence of 99% real-world accuracy. Real validation needs real data.

**Label windows are wider than the events.** Positive rates of 9–40% are inflated because
labels extend ±50–90 m around each event to give the model usable context. Operating
thresholds are therefore **not frequency estimates** — a 94% recall mud-loss threshold does
not mean 6% of hole is at risk. Every model card states this.

**Scores for wells already in the training corpus are optimistic.** The isolation forest has
seen them. A genuinely new well is scored honestly; a known well is not.

**The formation-risk anomaly detector separates weakly.** Measured separation against event
labels is AUC 0.597. It reliably finds *unusual* intervals and does not reliably find
intervals that became events. Its threshold is the top 5% score quantile, so the flag rate is
stable, but the signal is weak and the card says so.

**The NPT regressor explains little variance.** R² 0.068.

**Cementing issue is underpowered.** 288 rows across 48 wells. It is registered and
inactive.

**Everything is synthetic.** No real wells, no real reports, no real operational data.

**Eight known npm vulnerabilities** (2 moderate, 6 high) are outstanding.
