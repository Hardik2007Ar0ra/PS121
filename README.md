# NWIS — Nearby Wells Intelligence System

**Proactive drilling-risk intelligence from offset-well history.**

NWIS ingests drilling telemetry, well logs, and daily drilling reports; extracts structured formation and event data from documents; correlates active wells against nearby wells; and serves explainable risk predictions with per-well cross-validation.

Built for **SIH 2026 · Problem Statement 121 · Oil India Limited**.

---

The system integrates:

* Deterministic well, formation, depth-reference, telemetry, event, and document modelling
* Document ingestion and structured information extraction
* Geospatial offset-well correlation
* Hybrid lexical and semantic knowledge retrieval
* Seven machine-learning models across multiple risk categories
* Per-well cross-validation and deployment gates
* Explainable risk scoring
* Threshold-based alerting and alert lifecycle management
* Real-time telemetry ingestion and streaming
* React + Vite operational dashboard
* Authentication, validation, rate limiting, logging, and production configuration checks
* Versioned ML artifacts and model cards
* Deterministic synthetic data generation for reproducible evaluation

The complete system runs through a unified Node.js application architecture. SQLite provides the default zero-install runtime store, while the data-access layer supports PostgreSQL + PostGIS + pgvector as the production database configuration.

All development and evaluation data is synthetic. Wells, coordinates, telemetry, documents, and event labels are generated by a seeded simulator. The system is therefore suitable for demonstration, development, benchmarking, and technical evaluation; operational deployment requires validation against Oil India data.

## The problem

Drilling decisions are made against incomplete information. A driller reaches a formation that has been drilled before — often several kilometres away, by a different rig, under different mud conditions — and the knowledge that would inform the decision exists across paper logs, scanned reports, telemetry, and operational experience.

Three factors make this knowledge difficult to use:

1. **It is scattered.** Daily drilling reports, mud programmes, cementing job summaries, and event logs exist as separate documents and formats, including scanned reports.

2. **It is not directly comparable.** Offset wells use different depth references. An interval at 2,850 m MD in one well is not necessarily equivalent to 2,850 m MD in another. Explicit depth correlation is therefore required before comparison.

3. **It is retrospective.** Traditional reports primarily describe what has already happened. Drilling teams need intelligence about what is likely to happen over the next few hundred metres while the bit is still running.

NWIS addresses all three problems by converting historical drilling knowledge into a structured, searchable, correlated, predictive intelligence layer.

```text

│  Browser (React + Vite)                                         │
│  Overview · Wells · Risk · Events · Documents · Assistant       │
└────────────────────────────┬─────────────────────────────────────┘
                             │ REST + WebSocket
┌────────────────────────────▼─────────────────────────────────────┐
│  Express 5 API                                                   │
│  routes/ · middleware/ · auth/ (JWT access + refresh)            │
├──────────────────────────────────────────────────────────────────┤
│  Domain                                                          │
│  correlation/  offsets · sections · compare · lookAhead          │
│  alerts/       engine · rules · effectiveness                    │
│  ml/           train · serve · explain · registry · artifacts     │
│  nlp/          preprocess · segment · extract · relations         │
│  search/       embed · store · retrieve                          │
│  ingest/       pipeline · adapters                              │
├──────────────────────────────────────────────────────────────────┤
│  Data                                                            │
│  repositories/  typed access over relational schema              │
│  db/            SQLite · migrations · geo UDFs                   │
└────────────────────────────┬─────────────────────────────────────┘
                             │
              ┌──────────────▼──────────────┐
              │  PostgreSQL + PostGIS       │
              │  + pgvector                 │
              └─────────────────────────────┘
```

The runtime defaults to **SQLite** for a zero-install demonstration environment. PostgreSQL + PostGIS + pgvector provides the production database configuration.

Every database query passes through a repository layer. This keeps domain logic independent of the database engine and allows the storage backend to be changed without rewriting application logic.

The schema remains portable:

* PostGIS geography types provide production geospatial storage.
* pgvector provides dense vector storage.
* SQLite provides the local demonstration configuration.
* Repository interfaces remain consistent across both environments.

### Middleware stack

The API uses:

`helmet` · `cors` with an explicit allowlist · `express-rate-limit` · `compression` · `pino-http` request logging · `zod` request validation · `multer` file upload handling.

## The depth-reference rule

**Depth reference is the central invariant of the NWIS data model.**

Every depth value carries an explicit reference:

```text
depth_md_m     + depth_reference = 'MD'
depth_tvd_m    + depth_reference = 'TVD'
depth_tvdss_m  + depth_reference = 'TVDSS'
```

MD, TVD, and TVDSS are never compared across wells without explicit correlation.

Repository methods identify the reference system being compared, and the frontend displays the active reference on screen.

For example:

> 2,850 m MD in well A-17 and 2,850 m MD in well B-04 are not automatically treated as the same geological point.

The correlation layer establishes the relationship between those intervals.

# Machine learning

NWIS implements **seven models across three model families**, trained and served entirely in Node.js.

No Python runtime, scikit-learn installation, or dedicated model server is required.

## Why Node.js ML

The system is designed around a single application process that can run on operator hardware without requiring a GPU or separate ML runtime.

Using Node.js for the ML layer provides:

* One dependency tree
* One deployment process
* No Python runtime requirement
* No separate model server
* Directly inspectable model artifacts
* Deterministic inference
* Simplified on-premises deployment

The model artifact format is intentionally generic:

* model kind
* feature version
* feature list
* metrics
* model card
* trained parameters

This also allows externally trained models to integrate with the same serving layer when they emit the compatible artifact envelope.

---

## Algorithm layer

The algorithms are implemented in `server/ml/algorithms/`.

| Module               | Contents                                                                   |
| -------------------- | -------------------------------------------------------------------------- |
| `linalg.js`          | Numeric primitives and safe numerical operations                           |
| `metrics.js`         | ROC AUC, average precision, RMSE, R², bootstrap confidence intervals       |
| `logistic.js`        | L2 logistic regression, Adam optimisation, Platt calibration               |
| `tree.js`            | CART with single-sorted-sweep split search and stochastic boosting support |
| `gbdt.js`            | Gradient boosting, leaf shrinkage, row subsampling                         |
| `isolationForest.js` | Per-well isolation forest with context smoothing                           |
| `cv.js`              | Grouped k-fold and holdout splitting by well                               |

## Validation methodology

Cross-validation is grouped **by well rather than by row**.

A random row-level split would allow highly correlated depth intervals from the same well to appear in both training and validation data. That would artificially inflate performance.

NWIS instead holds out entire wells.

Therefore, every validation result measures performance on wells that the model has not seen during training.

Candidate algorithms compete on held-out metrics, and the winning algorithm is promoted. Runner-up performance is also retained in the model card.

### Key model findings

**1. Logistic regression outperforms gradient boosting on all four major classifiers.**

The engineered features have strong monotonic relationships with the target risks, allowing a linear boundary in logit space to outperform the more flexible booster.

The GBDT models remain available as evaluated runner-ups rather than being selected simply because they are more complex.

**2. Cementing Issue is registered but not activated.**

The model has only 288 rows across 48 wells and reaches an operating point with 0% precision. Activating such a model would generate operational noise without useful predictive value.

The deployment gate therefore keeps the model inactive.

**3. NPT prediction provides a measurable but modest improvement.**

The GBDT regressor achieves RMSE of 12.18 hours compared with a 12.61-hour baseline and an R² of 0.068.

The system reports this limitation directly rather than presenting the model as highly predictive.

---

## Deployment gate

NWIS does not activate a model merely because it has a high AUC.

A model must beat the "flag every depth interval" baseline and maintain a non-inverted ranking.

```js
metrics.deploymentGate = {
  usable,
  beatsAlwaysAlert,
  rankingNotInverted,
  reasons: [...]
};
```

The deployment gate is evaluated automatically during model evaluation and recorded in the model artifact.

---

## Explainability

Every model score has an associated explanation.

For logistic models:

```text
contribution = weight × feature_value
```

This provides an exact contribution for every feature.

For boosted models, the decision path through the trees is reported leaf by leaf.

Explanations are combined with operational guidance so that the system communicates not only **which variables influenced the prediction**, but also **what the prediction means in drilling terms**.

# Document intelligence

NWIS implements a document intelligence pipeline for drilling reports, mud programmes, cementing summaries, bit records, and related operational documents.

The pipeline performs:

1. **Acquisition** — ingest drilling reports, mud programmes, cementing summaries, and bit logs.

2. **Text extraction** — extract native PDF text using `pdfjs-dist` and process scanned pages using lazy-loaded `tesseract.js`.

3. **Page provenance** — record whether each page's text comes from native extraction or OCR.

4. **Segmentation** — divide documents into typed sections such as:

   * drilling summary
   * formation tops
   * mud
   * incidents
   * cementing
   * operational observations

5. **Entity extraction** — extract:

   * formations
   * depths
   * events
   * durations
   * mud properties
   * operational measurements

6. **Relation extraction** — connect extracted entities to:

   * wells
   * intervals
   * formations
   * telemetry
   * operational events

7. **Confidence scoring** — calculate extraction confidence using pattern specificity and corroborating information.

8. **LLM assistance** — optionally use an LLM for difficult extraction cases while retaining the deterministic extraction layer as the authoritative path.

The extraction pipeline remains functional without requiring an external model.

### Extraction quality

The system evaluates extraction quality against generator ground truth and reports precision and recall by entity type.

This allows document extraction performance to be measured quantitatively instead of being assumed from successful parsing.

# Search and retrieval

NWIS uses hybrid retrieval combining sparse lexical and semantic signals through **Reciprocal Rank Fusion**.

| Stage        | Implementation                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------ |
| Lexical      | SQLite FTS5 with BM25                                                                            |
| Tokenisation | `porter unicode61 remove_diacritics 2`                                                           |
| Vector       | Sparse TF-IDF with L2-normalised weighted term vectors                                           |
| Fusion       | Reciprocal Rank Fusion                                                                           |
| Corpus       | `knowledge_items` containing events, lessons, document chunks, well sections, and mud programmes |

The sparse retrieval architecture is deliberately designed for on-premises deployment.

It:

* requires no external embedding API
* requires no model server
* introduces minimal latency
* is deterministic
* is auditable
* runs on operator hardware

The system explicitly recognises that TF-IDF captures terminology rather than deep semantic meaning. pgvector provides the upgrade path for deployments with dense embedding infrastructure.

The search index is maintained through explicit `indexKnowledgeItem` calls on application write paths rather than hidden database triggers.

# Alerts and explainability

NWIS includes an operational alert engine built on top of the trained risk models and rule system.

## Alert rules

The rule engine supports:

* Threshold-based alerts
* Model-score alerts
* Rate-of-change alerts
* Cross-model agreement
* Formation and depth-context conditions

## Alert suppression

Repeated alerts from the same well and operational context are consolidated so that a single drilling issue does not produce dozens of redundant notifications.

For example:

```text
40 alerts from one well in one hour
                ↓
       suppression engine
                ↓
        one operational finding
```

## Alert lifecycle

Alerts follow:

```text
OPEN
  ↓
ACKNOWLEDGED
  ↓
RESOLVED
```

Each lifecycle transition records the responsible actor and reason.

## Alert effectiveness

Historical alerts are evaluated against subsequent events.

The system measures:

* Precision
* Recall
* Rule-level effectiveness
* Historical alert outcomes

This allows alert rules to be evaluated based on operational usefulness rather than only model metrics.

# Design decisions

### SQLite now, PostgreSQL in production

All application queries use repositories. This isolates domain logic from the underlying database implementation.

PostGIS and pgvector provide the production equivalents for geospatial and vector operations.

### Node-only ML

The ML stack runs in the same ecosystem as the API and frontend tooling.

This provides a single deployment model and keeps model artifacts directly inspectable.

### Sparse TF-IDF + BM25

The retrieval system prioritises on-premises operation, transparency, deterministic behaviour, and low infrastructure overhead.

### Depth reference is never implicit

Depth is always accompanied by MD, TVD, or TVDSS semantics.

This prevents physically invalid cross-well comparisons.

### Causally derived synthetic labels

Synthetic event labels are derived from simulator mechanics.

For example, mud loss is generated when simulated ECD crosses a simulated fracture gradient rather than simply assigning the label independently.

This allows the complete extraction → feature engineering → prediction pipeline to be evaluated consistently.

### Application-level indexing

Knowledge indexing is performed explicitly by the application rather than hidden database triggers.

This makes indexing behaviour observable and testable.

### LLM is optional

The deterministic extraction pipeline remains authoritative.

An LLM can assist difficult cases without becoming a mandatory dependency for the core system.

### Failed models remain visible

Models that fail deployment gates remain registered with their metrics and failure reasons rather than being silently removed.

This preserves the audit trail of model selection.

# Limitations

The system explicitly separates **demonstration performance** from **real-world operational performance**.

### Synthetic data

All current wells, reports, telemetry, coordinates, and event labels are synthetic.

The reported metrics therefore measure the ability of the complete pipeline to model the synthetic drilling environment. They do not constitute evidence of equivalent performance on Oil India field data.

### Event-label windows

Positive labels extend approximately ±50–90 m around events to provide usable modelling context.

Consequently, positive rates of 9–40% are not direct estimates of real-world event frequency.

An operating threshold such as 94% recall for mud loss therefore does not mean that 6% of the hole is safe.

### Known-well scores

Models trained on a particular synthetic corpus naturally produce more optimistic scores for wells already represented in that corpus.

The grouped cross-validation results provide the primary measure of generalisation to unseen wells.

### Formation-risk anomaly detection

The formation-risk anomaly detector achieves a separation AUC of 0.597 against event labels.

It is therefore best interpreted as a detector of unusual intervals rather than a deterministic event predictor.

Its operating threshold is the top 5% score quantile.

### NPT prediction

The NPT model achieves:

```text
RMSE = 12.18 h
Baseline RMSE = 12.61 h
R² = 0.068
```

The model therefore explains only a modest proportion of NPT variance.

### Cementing Issue

The Cementing Issue model contains only 288 rows across 48 wells and remains inactive because its deployment gate is not satisfied.

### External operational integrations

Production integration requires confirmation of Oil India telemetry interfaces, real report formats, data-sharing permissions, and deployment policies.

### Security and dependency maintenance

The production deployment is maintained with dependency auditing and security updates as part of the deployment process.
